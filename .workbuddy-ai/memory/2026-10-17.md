## 回复框功能面板重构（同日）

**目标**：消除重复渲染、修复键盘避让与功能面板互相抢高度。

**根因诊断**（`components/comment/CommentComposerModal/CommentComposerModal.tsx`，原 1222 行）

1. **每帧两次 setState**：`animatedPanelHeight` 与 `reservedKeyboardHeight` 各由一条 `Animated.Value.addListener` 驱动，动画期间 60fps 全组件重渲染。
2. **5 套键盘监听打架**：RN `Keyboard.addListener(willShow/willHide)` + `KeyboardEvents(didShow/didHide)` + `KeyboardEvents(willShow/willHide)` + `useKeyboardState` + 单独的 didShow 订阅；每套都调 `scheduleSnapToIndex`，同一帧 snapToIndex 被调 4~5 次。
3. **三个 ref 互相试探**：`pendingPanelModeRef` / `pendingKeyboardOpenRef` / `shouldFocusKeyboardRef` 表达「键盘收完再开面板」，过渡期 `accessoryHeight` 会短暂归零导致 sheet 掉高再回来。
4. **面板按高度条件挂载**：`visiblePanelMode === "emoji" && panelHeight > 0`，收起动画一开始就卸载 EmojiPanel（内容瞬消），再打开重新拉一遍表情图。
5. **focus 重试 6 次**：`[0,32,96,180,320,520]`，每次触发 onFocus → 额外 6 次 snapToIndex。
6. **`RichComposerInput` 的 effect 依赖 `onReady`**：父组件每次重渲染都重建 onReady → effect 重跑 → `clearKeyboardTarget()` 清掉 BottomSheet 的键盘目标，表现为「键盘起来了 sheet 不跟」。
7. **Android adjustResize 压缩 window**：`useWindowDimensions().height` 变小 → `maxAccessoryHeight` 变小 → 键盘收起/面板展开途中面板被裁。

**重构方案**

- 引入 `DockMode = "none" | "keyboard" | "panel"` 单一状态机；键盘与面板**共用同一占位高度**（都取实测键盘高度），切换时 sheet 高度不变、只有内容互换。
- 删除两条逐帧动画链路（`animatedPanelHeight` / `reservedKeyboardHeight` / `animateReservedKeyboardHeight` / `keyboardHeightAnimatedValue` / `isClosingPanelRef` / `previousTargetRef`）。
- 键盘监听收敛为 `useKeyboardState` + 一个 `keyboardDidShow` 记录高度。
- `scheduleSnapToIndex` 补偿从 5 处收到 2 处（主动 + 90ms 兜底）。
- focus 重试 `[0,64,200]` + 一次 260ms 兜底，`onFocus` 触发即 `clearFocusRetryTimers()`。
- 面板改为「打开过一次后常驻挂载 + `display: none` 隐藏」，保住滚动位置、零重新挂载。
- `layoutWindowHeight` 用 state 记住「无键盘时的窗口高度」，键盘可见且 window 变小时忽略，只采纳旋转/分屏。
- 键盘态改用 `rawKeyboardHeight` 实测值，首次打开不再按默认 300 跳一次。
- `EmojiPanel` / `RichComposerInput` 加 `memo`；`RichComposerInput` 的 `onReady/onFocus/onBlur/onPress` 走 ref，切断 effect 依赖。
- `handleInputFocus` 里若 `dock === "panel"` 则强制关面板（键盘被外部唤起时让位）。

## 键盘时序与面板高度三修（同日续）

用户反馈三条，全部定位到「高度变化的时序」这一族问题。

### 1. 虚拟键盘关闭后 sheet 要等一会儿才缩下去

**根因**：`useKeyboardState` 内部只监听 `["keyboardWillShow", "keyboardDidHide"]`
（见 `node_modules/react-native-keyboard-controller/src/hooks/useKeyboardState/index.ts:8`）。
显示走 willShow（动画开始就有高度），收起走 didHide（动画结束才归零）。
于是 sheet 在整段 ~250ms 收起动画里保持原高度，动画结束再瞬间掉下来。

**修法**：自己订阅 `KeyboardEvents.addListener("keyboardWillHide")`，在动画开始就
`setDock("none")`，并用 `event.duration` 作为 `snapToIndex(0, { duration })` 的时长
（gorhom 的 `animate.ts` 见到 `duration` 会从 spring 切成 timing），两者同步收。

**踩坑**：`sheetHeight` 变化会触发定位 effect 里的 `scheduleSnapToIndex()`（无时长，
走 spring），把 willHide 设好的时长覆盖掉。改为用 `snapDurationRef` 传递时长，
effect 里的调用也能读到，用完即清。`onDismiss` 里也要清。

原来的 `keyboardVisible` effect 保留为兜底（Android 11 以下没有 willHide）。

### 2. 选图后不自动弹起键盘

**根因**：`handleImagePress` 只处理了「sheet 被系统关掉要重新 present」，
从来没有还焦点。相册是原生页面，打开必然失焦收键盘，返回后停在
「既没键盘也没面板」的中间态。

**修法**：进相册前记 `shouldRestoreKeyboard = dock === "keyboard" || isInputFocusedRef.current`；
返回后 `settleAfterPicker()` 统一收尾（重新 present + `restoreKeyboardAfterPicker(delay)`）。
`settleAfterPicker` 用 `settled` 标志保证幂等，`finally` 里再兜一次异常路径。
delay 取 `PICKER_RESTORE_FOCUS_DELAY_MS = 240`，重新 present 时 +120。

### 3. 聊天页开面板时聊天记录被上顶 + 多余内容高度

**根因**：面板是行内渲染在输入行下方的，撑高 `KeyboardStickyView` 的同时
已经让 `chatArea`（flex:1）等量收缩 —— 列表视口本身就矮了一截。
而 `handlePanelLayout` 又把 `BASE_BOTTOM_HEIGHT + panelHeight` 上报给
`extraContentPadding`，等于同一个高度被预留两次：
内容被上顶两次，最后一条消息和输入框之间多出一块 panelHeight 的空白。

**修法**：`handlePanelLayout` 只保留 `freeze.value = false`，不再上报高度。

**自洽性验算**（结论：in-flow 布局下 extraContentPadding 应恒为 0）：
- 键盘关：bar 在流内，chatArea 底 = bar 顶，无需额外 inset。
- 键盘开：`KeyboardStickyView` 只做 translateY 不改布局，bar 上移 K 遮住列表底部 72px；
  同时 `KeyboardChatScrollView` 抬升 K，最后一条消息正好落在 bar 顶上。两者抵消。
- 面板开：bar 在流内长高 P，chatArea 等量收缩 P，消息上移 P 后紧贴 bar。不需要 inset。

## 聊天键盘几何 + 通知类型图标（同日续二）

上一轮回复框的改动已由用户提交为 `2a0ba98 feat: optimize emoji panel rendering and keyboard handling`。

### A. 聊天页键盘弹起后页面被上顶

三条独立成因，全部指向「高度被重复计入」：

1. **`keyboardLiftBehavior="persistent"`**（`VirtualizedListScrollView`）
   该模式按「底部栏浮在列表上方」的场景设计，键盘收起后**不回落**。本页底部栏是
   行内布局（撑高即压缩 `chatArea` 视口），所以收起键盘后列表永久多出 K 高度空白。
   改为 `"always"`。

2. **`KeyboardStickyView offset.opened = +safeBottom`**
   已从原生确认 `keyboardHeight = keyboardFrame.size.height`
   （`ios/observers/movement/observer/KeyboardMovementObserver+Listeners.swift:15`），
   即 **含底部安全区**。而底部栏静止底边已经在安全区之上，所以只需上移 `K - safeBottom`。
   原来 `+safeBottom` 让整条栏多上移 `2*safeBottom`，栏与键盘之间露出一截列表。
   改为 `opened: -safeBottom`。

3. **`KeyboardChatScrollView` 的 `freeze` 造成 padding 卡死**
   `freeze.value = true` 会同时挡掉键盘动画的 `onStart` 与 `onEnd`
   （`useChatKeyboard/index.ios.ts:67` 与 `:232`），而之后没有任何事件会重算 padding。
   「键盘 → 面板」时 freeze 住，键盘收起后 padding 停在 K 不归零 → 用过一次面板，
   列表就永久被顶上去一段。删掉该分支的 freeze（面板 → 键盘方向保留，靠 onInputFocus 解除）。
   `handlePanelLayout` 随之失去唯一职责，一并删除。

**不变量**：`KeyboardChatScrollView.offset === -KeyboardStickyView.offset.opened`。
两者都表达「底部栏相对列表视口底边要移动多少」，写反一个方向就会多顶或少顶。

## Profile Hero 下拉刷新改原生样式 + 逻辑收口（同日续五）

### 为什么不能直接用 RefreshControl

`app/(tabs)/profile.tsx` 的滚动容器是 `@sdcx/nested-scroll` 的 `NestedScrollView`，
它的 props 只有 `ViewProps & { contentContainerStyle, bounces }`，**不透传 refreshControl**，
所以挂不上 RN 原生 `RefreshControl`。外层 `@sdcx/pull-to-refresh` 的 header 是
`RCTCustomPullToRefreshViewProtocol`（iOS）/ SmartRefreshLayout header（Android），
视觉完全由自绘决定，系统不会画菊花。

### 改动

**`components/profile/NativePullToRefreshHeader.tsx`（重写）**

- 自绘空心圆（20×20 border 圆 + scale/opacity）→ 原生 `ActivityIndicator size="small"`。
  iOS 即 `UIActivityIndicatorView`，Android 即 `ProgressBar`，颜色取 `theme.mutedForeground`
  （原生灰，不再用品牌蓝）。
- 删除 `idle/pulling/ready/refreshing` 四态机与 `progress` state：原来每次 offset 变化都
  `setState`，下拉全程 60fps 重渲染。改为 `Animated.Value` + `setValue`，零 setState。
- 删除 `onStateChanged` 订阅；`refreshing` 单一真源，不再 `state === "refreshing" || refreshing` 双判。
- 进度映射：opacity `[0, 0.35, 1] → [0, 0.45, 1]`，scale `0.7 → 1`。
- `Animated.Value` 用 `useState(() => new Animated.Value(0))` 持有 —— `useRef().current`
  会被 `react-hooks/refs` 判为渲染期读 ref（该规则在本项目已开启）。

**`app/(tabs)/profile.tsx`**

- `<PullToRefresh>` 删掉 `refreshing` / `onRefresh`：有自定义 header 时库内部
  `renderHeader()` 直接返回 header，这两个 prop 是死参数（`PullToRefreshNativeComponent`
  的 NativeProps 里也没有它们）。
- `handleRefresh`：`finally` 改为顺序执行 + **最短展示 350ms**（`MIN_REFRESH_VISIBLE_MS`），
  避免接口秒回时菊花一闪；依赖数组补上漏掉的 `heroContainerHeight`。
- `renderScene` 依赖从 `[handleRefresh, handleTabScroll, refreshing, refreshSignal]`
  收敛为 `[handleTabScroll, refreshSignal]` —— 原来 `refreshing` 一变，5 个 tab 全部重渲染。

**5 个 tab 组件**（Posts/Comments/Favorites/Topics/History）：删除从未被使用的
`refreshing` / `onRefresh` props（类型 + 解构）。各 tab 的刷新只靠 `refreshSignal` 自增驱动。

### 关键结论

- `REFRESH_TRIGGER_DISTANCE = 80` 既是 header 高度也是原生触发距离，两者必须一致，
  否则「进度满了但松手不刷新」。
- 刷新结束后的 Hero 回弹**必须**保留手动 `Animated.timing`：Android `onMoving` 在
  `RefreshFinish` 状态下不再上报 offset，iOS 同理，光靠 offset 回调收不回去。
- `ActivityIndicator` 无法「静止但可见」（`animating=false` 时 iOS 隐藏），所以下拉阶段
  只能是「转动 + 渐显」，做不到 iOS 原生那种静止菊花。

**校验**：header 文件 ESLint 零告警；`tsc` profile 相关零错误；`profile.tsx` 仅剩存量
`react-hooks/refs` 错误（`useRef(new Animated.Value()).current` 的既有写法）。




## 主色审计 + 聊天气泡尾巴（同日续三）

### A. 主色审计结论：`primaryFill` 不是错色

用 HLS 拆开三个主色值，确认它们同色相、只差明度：

| Token | 值 | 色相 | 明度 | 白字对比 |
| --- | --- | --- | --- | --- |
| `primary`（品牌） | `#6680ff` | 229.8° | 70% | 3.44:1 |
| `primaryFill` | `#4C63E6` | 231.0° | 60% | 4.96:1 |
| `primaryText`（暗） | `#8FA2FF` | 229.8° | 78% | — |

ΔH 仅 1.2° —— 按钮比图标深一档是**明度角色差异**，不是用了别的蓝。
`#6680ff` 配白字只有 3.44:1，13~15px 标签达不到 AA 4.5:1，所以必须拆。

**真·错误是色相跑偏**：`MessageIcons.tsx` 原硬编码
`#6E63FF`(H244°) / `#A784FF`(H257°) / `#8F7BFF`(H249°) / `#C9B6FF`(H256°)，
偏离品牌色 14°~27°，会读成「另一个蓝」；`#F3F6FC` 这类亮填充在暗色模式下是亮色块。

修法：`MessageIcons` 全部改成从 `theme` 派生（`${theme.primary}4D` / `26` / `B3` / `CC`），
`app/(tabs)/messages/index.tsx` 的 `#c9b6ff50` / `#ffd8b050` 改为
`${theme.primary}26` / `#F59E0B26`（琥珀与 notificationKind 的 system 同源）。
