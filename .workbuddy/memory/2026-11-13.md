## 经验：patch-package 在 Windows 上重新生成补丁

`npx patch-package <pkg>` 会因 `node_modules/<pkg>/android/build/.transforms/...`
路径过长（git warning: Filename too long）直接以 status 128 失败，`--exclude`
无效。可行做法：先把两个包的 `android/build` 临时 `mv` 到项目外，
生成补丁后再移回：
`mv node_modules/<pkg>/android/build ../_tmp && npx patch-package <pkg> ... ; mv ../_tmp ...`
生成后用 `git apply --check --reverse -p1 --ignore-whitespace patches/<pkg>.patch`
校验补丁与当前 node_modules 一致。本次两个补丁均通过。

原生改动需要重新编译 native app 才生效（`expo run:android` / `run:ios`）。

## 追补：插入视频链接 sheet 弹在键盘底下（真机反馈）

上一轮把「键盘没弹出」理解成焦点问题，真机实际是 **sheet 弹出来了但被键盘压住、
完全没做键盘避让**。改动只在 `components/publish/InputSheet.tsx`。

**根因（读 `@gorhom/bottom-sheet` v5.2.14 源码确认）**：
- `src/hooks/useAnimatedKeyboard.ts` 只靠 `Keyboard.addListener('keyboardDidShow')`
  更新内部 `animatedKeyboardState`。键盘在点工具栏**之前**就已被正文编辑器唤起，
  sheet 挂载得晚，收不到那次 SHOWN → 状态一直是 `UNDETERMINED / height 0`，
  库认为没有键盘，面板按全屏底部定位，正好在键盘后面。
- `BottomSheet.tsx:1692-1708`：Android + `android_keyboardInputMode="adjustResize"`
  + `keyboardBehavior="interactive"` 时库把 `heightWithinContainer` 置 0 **并 return**，
  主动放弃位移，指望 window 缩小；而 `KeyboardProvider` 接管 WindowInsets 后
  并不保证 window 会 resize（尽管 AndroidManifest 里配了 `adjustResize`）。
- 所以「先收键盘再弹 sheet」虽能触发新事件，Android 上仍不位移，不是正解。

**修法**：不依赖 gorhom 的键盘事件，改用 `useKeyboardState`
（react-native-keyboard-controller 的全局 store，Provider 从根节点就一直有值，
与 sheet 挂载时机无关）算出 `keyboardInset`，传给 `BottomSheetModal` 的
`bottomInset` —— `BottomSheetHostingContainer` 会把它作为容器的 `bottom`，
把整个 sheet 抬到键盘上沿。`BottomSheetModalProps` 继承 `BottomSheetProps`
（只 Omit 掉 `containerHeight`/`onClose`），所以 `bottomInset` 合法。

配套：
- `keyboardBehavior` 从 `interactive` 改成 **`extend`**：单档位时
  `getEvaluatedPosition` 返回 `highestDetentPosition` = 当前位置，库不会再二次位移
  （interactive 在 iOS 会和 bottomInset 叠加把面板抬两次）。
- `snapPoints` 加下限 240：Android 键盘弹出会压缩 `windowHeight`，
  原来 `0.3 * windowHeight` 会矮到放不下输入框。
- 保留上一轮的 `requestKeyboardFocus` 多次重试 + 自动聚焦。

**同类隐患（本次未改）**：`InlinePostSheet` / `TopicPickerSheet` 同样从工具栏、
在键盘已显示时打开；InlinePostSheet 顶部有输入框且同样配了
`interactive + adjustResize`，如真机也出现可照此套 `bottomInset` 处理。
凡是「键盘先于 sheet 显示」的 bottom sheet 都会踩这个坑。

验证：eslint 零问题；tsc 仍只有 188 个 codegen `Null` 错误，改动文件零错误。
上一轮的三项改动已被用户提交为 `c3cd786`，本轮工作区只有 InputSheet 一个文件。

## 修复：前端选 GIF 被压成静态图

**根因（读 expo-image-picker@56 原生源码确认）**
- Android `MediaHandler.handleImage`：`quality != 1` 走 `CompressionImageExporter`，
  先解码成 Bitmap（GIF 只有首帧）再按扩展名压成 PNG/JPEG；`quality == 1`
  （`ImagePickerConstants.MAXIMUM_QUALITY`）才走 `RawImageExporter` 原样拷贝。
  且产出文件仍叫 `*.gif`、asset.mimeType 仍是 `image/gif`，字节已是 PNG —— 三重不一致。
- iOS `ImageUtils.readDataAndFileExtension`：`quality >= 1 && !allowsEditing &&
  preferredAssetRepresentationMode == .current` 才走快路径；否则 JPEG 重编码
  （GIF 有独立 `processGifData` 分支，但要走到那个分支）。
- 所以「选图 `quality < 1`」本身就是 GIF 杀手，压缩必须自己做。

**改动**
- `lib/uploadImage.ts`：新增 `isGifSource()` + `IMAGE_MIME_BY_EXT`（含 gif/heic）；
  `prepareContentImage` 开头短路 GIF，新增可选 `mimeType` 参数；
  `uploadSingleImage` 改用映射表并给文件名加随机后缀（原来 9 张图并行上传
  都用 `Date.now()`，同毫秒会重名）。
- `app/publish/index.tsx`：图片帖 `quality 0.9 → 1`；提交时**串行**逐张
  `prepareContentImage`（9 张原图并发解码会 OOM）再并行上传。
- `components/publish/ArticleRichTextToolbar.tsx`：插图 `quality 0.9 → 1`，
  并把 `asset.mimeType` 传给 `prepareContentImage`。
- 未改：评论/认证材料本来就是 `quality: 1`，`imageUpload.ts` 的 `shouldCompress`
  也已 `mimeType !== "image/gif"`；封面/头像/背景走 `ImageCropperSheet`
  （allowsEditing + JPEG）本就是静态产物，属预期。

**遗留待确认**：服务端 `/upload/config` 的 `allowedMimeTypes.image` 是否含
`image/gif`。不含的话评论链路的 `mustConvertType` 会强制转码，GIF 仍会变静态。

## 修复：选视频时闪退（`components/publish/VideoFrameSheet.tsx`）

**根因**：`VideoFrameSheet` 在发布页是常驻挂载的，抽帧 `useEffect` 的依赖是
`[duration, videoUri]` —— 用户在相册里一选完视频，`setVideo()` 触发重渲染，
**还没点「从视频截取封面」，后台就已经在抽 8 帧了**。两个致命点：

1. Android 侧 `generateThumbnailsAsync` 内部（`VideoModule.kt:337`）是拿**同一个**
   `MediaMetadataRetriever` 起 8 个并发 `getFrameAtTime`（`OPTION_CLOSEST`），
   等于同时解 8 张原尺寸位图：4K 视频峰值近 300MB → OOM / 原生崩溃（闪退）。
   `VideoThumbnail` 的 `getAdditionalMemoryPressure()` 还会把 byteCount 报给 Expo，
   内存压力直接顶格。
2. 只传 `maxWidth` 时 Android `VideoThumbnailOptions.toNativeSizeLimit()` 用
   `Int.MAX_VALUE` 补 height，部分 OEM 的 `getScaledFrameAtTime` 会按这个上界算尺寸。
3. effect cleanup 里 `player.release()`：抽帧 Promise 还没落地就释放播放器，
   原生侧拿到已释放引用，同样会崩。

**改法**
- `present()` 里置 `open=true`，抽帧 effect 增加 `open` 门槛：不打开面板零解码。
- 抽帧改为**串行**：`for (time of times) await player.generateThumbnailsAsync([time], ...)`
  —— 每次只起 1 个 retriever 调用，顺便让缩略图逐张渲染。
- 同时传 `maxWidth: 640 / maxHeight: 360`，不再让库自己补 `Int.MAX_VALUE`。
- `player.release()` 从 cleanup 移到抽帧 async 的 `finally`；cleanup 只置
  `cancelled` 标记，让在途请求自然结束后再释放。
- `createVideoPlayer` 包 try/catch，uri 失效时置 `failed` 而不是抛出。
- `onDismiss` 清空 `frames`（原生位图引用，留着会占内存）。
- 新增 `publish.videoFrame.failed` 文案（zh/en）：取帧失败或拿不到 duration
  （编辑态回填的远端视频）时显示提示，不再无限转圈。
- 新增 `THUMB_MAX_HEIGHT = 640 * 9 / 16`。

**验证**：eslint 零问题；tsc 无新增错误。`VideoFrameSheet` 目前只在发布页
「视频」类型下使用，无独立视频编辑器页面。

## 视频编辑器闪退加固（打开面板即崩）

用户反馈「编辑视频时闪退」。排查 expo-video 56 原生实现后的结论与改动：

**根因方向**
- `extractVideoFrames` 之前**自建第二个 ExoPlayer**：预览已经有一个播放器在解码，
  抽帧又建一个，Android 上硬件解码器实例翻倍，低端机 codec 申请失败或原生崩溃。
- `isReady` 在 loading ↔ readyToPlay 抖动时 effect 重跑 → **反复抽帧、反复建播放器**。
- `Slider` 用 `displayTime` 做受控 value，拖动时手指位置与 JS 回灌同时写值，
  Android 上易抖/崩。

**改动**
- `lib/video.ts`：`extractVideoFrames(player, times, opts)` 改为**复用传入播放器**，
  不再 createVideoPlayer / release；新增 `seekVideoPlayer(player, seconds)`
  （把不可避免的 `currentTime` 赋值收进 lib，避开 react-hooks/immutability）。
- `VideoEditorSheet.tsx`：
  - 抽帧前 `player.pause()`；`requestedUriRef` 保证同一 uri 只抽一次（失败才允许重试）
  - Slider 的 `value` 改用 `currentTime`，`onSlidingStart` 置 `seekingRef` 冻结
    timeUpdate 回写，拖动期间只更新 `seekValue` 用于显示 → 不回灌控件
  - `snapPoints` 用 `useMemo`（每次新数组会让 BottomSheet 重算布局）
  - 帧条抽成 `memo(FrameStrip)`，`onSelect` 用 useCallback 稳定引用，
    避免 timeUpdate 每 0.2s 重绘 10 张缩略图
  - 删除卸载期 `player.pause()` 的 cleanup：`useVideoPlayer` 的 release 会先执行，
    之后再碰 player 会抛「已释放」

**已验证的平台事实**
- `surfaceType` 是 Android 属性，通过 `NativeTextureVideoView` 实现，用法正确
- expo-image 的 Android 端接受 `SharedRef<Bitmap>`，`VideoThumbnail` 正好是它，
  `source={thumbnail}` 安全
- `generateThumbnailsAsync` 每次新建 MediaMetadataRetriever 并在 safeUse 里 close，
  串行调用不会复用已关闭的 retriever

**验证**：eslint 零问题；tsc 无新增错误。仍需真机 logcat 确认是否彻底解决。

## 视频闪退真正根因：media3 版本钉错（AbstractMethodError）

**崩溃栈**：`java.lang.AbstractMethodError: abstract method
"androidx.media3.exoplayer.upstream.Allocator androidx.media3.exoplayer.LoadControl.getAllocator()"
on receiver expo.modules.video.player.VideoPlayerLoadControl`

**根因**：expo-video 56 起以**预编译 AAR** 分发
（`node_modules/expo-video/local-maven-repo/host/exp/exponent/expo.modules.video/<ver>/*.aar`），
POM 声明 media3 **1.9.0**。而 `android/build.gradle` 的 `@media3-pin` 把 media3
force 到 **1.8.0**（当初为迁就 react-native-video 6.19.2 按 1.8.0 编译）。结果 AAR 里的
`VideoPlayerLoadControl : DefaultLoadControl()` 缺 `getAllocator()`，
ExoPlayerImplInternal 一调就抛 AbstractMethodError —— 打开视频/抽帧即闪退。

**为什么之前反过来也会崩**：RNV 6.19.2 用 `super(...)` 调 DefaultLoadControl 的
旧构造器，运行在 1.9.0 上抛 NoSuchMethodError。两个库对 media3 的编译期版本打架，
无论钉哪一边都会崩掉另一边。

**修复**
1. `react-native-video` 6.19.2 → **6.19.3**：该版本改用 `DefaultLoadControl.Builder`
   构建，并同时声明 `getAllocator()` / `getAllocator(PlayerId)`（不加 @Override，
   后者用反射），官方注释明确写了「app 可能解析到比库编译时更新的 media3」。
2. `android/build.gradle` `@media3-pin` 的 `pinnedMedia3Version` 1.8.0 → **1.9.0**，
   与 expo-video AAR 的编译版本对齐。

**验证**：`./gradlew :react-native-video:compileDebugJavaWithJavac` 通过（只有 deprecation
警告）；dependencyInsight 显示 debugRuntimeClasspath 全部解析为 1.9.0；tsc 无新增错误。

**教训**：expo SDK 56 的 expo-* 模块是预编译 AAR，其 media3 版本不可被 force 降级；
遇到 media3 冲突要让「从源码编译」的那一方（RNV）去兼容运行时版本。

## 视频编辑器：进度条手势 + 自由选帧

**问题 1：进度条拖不动 / 一拖面板跟着走**
面板用 `BottomSheetModal`，内容区的 pan 手势会接管原生 SeekBar 的横向拖动，
轻微上下抖动还会被判定成下拉关闭。

修复：`enableContentPanningGesture={false}`。内容区不再接管拖拽，进度条与
横滑帧条归控件自己；面板仍可从顶部把手拖动关闭（默认 handle 保留），
遮罩点击和右上角关闭按钮不受影响。

**问题 2：自由选帧不成立**
- 点帧条只 `setChoice`，预览不跟随 → 现在 `seekVideoPlayer(requestedTime)`
  且先 `pause()`，选中的帧和画面一致
- 「用当前画面」读的是 `currentTime` 状态（0.2s 才刷一次）→ 改为读
  `player.currentTime` 实时值
- 进度条本身成为选帧入口：松手 → 定位 → 自动抓帧选中（index=null，
  帧条不高亮任何一格）；拖动过程中按 ~250ms 节流 seek，能边拖边看画面

**节流与并发**（防止低端机/4K 拖崩）
- 文案只在整秒变化时 `setState`，否则每帧重渲染会和原生滑块抢 UI 线程
- 松手抓帧延迟 120ms 合并，连续拖动只取最后一次；`captureSeqRef` 丢弃过期的
  抓帧结果；`handleDone` 前清理未落地的定时器，避免覆盖已选封面

**验证**：eslint 零问题；tsc 无新增错误。文案 `publish.videoEditor.hint` 改为
提示可拖动选帧。
