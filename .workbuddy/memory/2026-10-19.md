## iOS 侧补齐同一批能力

iOS 与 Android 架构完全不同（Android 是 Span，iOS 是 `StyleBase` 子类 +
`StyleType` 枚举 + marker attribute）。最终没有走「改 HTML 字符串」的捷径，而是按
正规扩展点新增了一个 `CharacterStyleBase` 基类和三个子类。

关键设计：marker attribute 里直接存 UIKit 值（`UIColor` / `NSNumber`），
`applyStyling:` 再把它展开成真正负责渲染的属性。这样才契合
`InputAttributesManager.handleDirtyRangesStyling` 的「先 setAttributes 重置成默认，
再按 StylePair 重放」机制 —— 否则每次编辑后颜色 / 字号都会被冲掉。

新增文件（7 个）：
- `ios/extensions/CssStyleUtils.{h,mm}`：CSS 值 ⇄ UIKit 值
  （`#rgb/#rgba/#rrggbb/#rrggbbaa` / `rgb()` / `rgba()` / 少量颜色名；
  `em`、`%` 因缺父级字号信息直接判无效）。
- `ios/interfaces/CharacterStyleBase.h` + `ios/styles/CharacterStyleBase.mm`：
  覆写 `styleCondition:range:`（基类比的是 `@"AnyValue"`，这里改成判断值类型，
  不改的话 `detect:` 永远失败）、`applyStyling:`、`addTypingWithValue:`、
  `reapplyFromStylePair:`。
- `ios/styles/TextColorStyle.mm` / `TextBackgroundStyle.mm` / `FontSizeStyle.mm`。

修改的既有文件：`StyleTypeEnum.h`（加 3 个枚举，放在 `Strikethrough` 之后）、
`StyleHeaders.h`、`EnrichedTextStyleHeaders.h`（viewer 变体，必须与
`StyleUtils.mm` 里 baseClasses / viewerClasses 的顺序一一对应）、
`EnrichedTextStyles.mm`、`StyleUtils.mm`、`HtmlParser.mm`（`<span style>` 解析，
一个 span 拆成最多 3 条 processed style，因为 `applyProcessedStyles:` 只接受
「一个类型 + 一个 StylePair」；序列化走 `tagContentForStyle:` 返回
`span style="color:..."` / `span`）、`InputHtmlParser.mm`、`TextHtmlParser.mm`、
`EnrichedTextInputView.mm`（`applyCharacterStyle:cssValue:` 统一入口 + 3 个命令分支）。

坑与结论：
- `FontSizeStyle` 不能按基类那样把 `NSNumber` 塞给 `NSFontAttributeName`，
  必须 `enumerateAttribute` 后 `[font setSize:]`，否则崩；用 `setSize:` 而不是
  重建字体，粗体 / 斜体 traits 才能保住（顺序无关，`setBold` 也保留字号）。
- 故意**不**覆写 `appliesStylingToTyping` / `applyStylingToTypingAttrs:`。
  那条钩子绕过了 `_removedTypingAttributes`，光标收起时点「清除格式」会被
  前一个字符的颜色重新灌回去。保持与 `BoldStyle` 一致（默认 NO，靠
  dirty range 重放）才正确。
- 新增 7 个 .mm，podspec 的 `ios/**/*.{h,m,mm,cpp}` 是通配，但**必须重新
  pod install**，否则 Xcode 工程里不会出现这些编译单元。

验证：`npm pack` 取干净包 → `git apply --check` 通过 → 应用后 iOS 树与本地
`node_modules` 逐字节一致（仅 CRLF 差异）。本机无 macOS / Xcode，真实编译待验证。

iOS 生效步骤：`npx expo prebuild --platform ios`（或 `cd ios && pod install`）
后用 Xcode 重新编译。JS 侧调用的是同一批方法名，`ArticleRichTextToolbar`
无需改动。

## 文章编辑器：图片回填 / 光标主题色 / 样式对齐 web

### 1. 图片回填失败的真因

`react-native-enriched-html` 的图片是**按 `width` / `height` 分配版面**的：
iOS `MediaAttachment.bounds = (0, 0, width, height)`，Android
`getDrawable()` 里 `setBounds(0, 0, width*scale, height*scale)`。
web 端 Quill 存的是 `<div class="ql-image-wrapper"><img src="..."></div>`，
**没有尺寸**，于是附件被排成 0×0 —— 看起来就是「图片没回填」。

新增 `lib/editorHtml.ts`：

- `prepareArticleHtml(html, contentWidth)`（回填用）
  - `ql-size-*` → `<span style="font-size:Npx">`（原生字号只能挂 span）
  - `ql-align-*` → `style="text-align:..."`（原生按 style 读对齐）
  - 删 `.ql-image-caption`（web 独有的可编辑图注，原生没有对应结构）
  - `div.ql-image-wrapper` → `<p><img/></p>`，每张图单独成段，否则连续图片挤一行
  - `img` 的 `src` 过 `normalizeImageUrl`（http→https、相对路径补 origin），
    缺尺寸时用 `Image.getSize` 量，**有尺寸就不再量**（保证幂等）
  - 量不到时兜底 `contentWidth × 0.5625`
- `toArticleHtml(html)`（提交用）：把裸 `<img>` 包回 `div.ql-image-wrapper`，
  否则 web 端 Quill 的 image blot 认不出（它的 blot 是 `div.ql-image-wrapper`），
  再从网页编辑一次图片全丢。**故意不带回 width/height**：web 靠
  `max-width:100%` 自适应列宽，写死宽度在桌面端会缩水。

接入点：`app/publish/index.tsx` 编辑回填 `await prepareArticleHtml(...)`（同时用它
作为撤销栈种子，否则撤销回退到原始 HTML 图片又会消失）；提交时 `toArticleHtml`。

### 2. iOS 光标不是主题色

`cursorColor` 在 iOS 侧是**死属性**：`EnrichedTextInputView.mm` 只处理
`selectionColor` 并塞给 `textView.tintColor`，而 UIKit 的光标和选区都由
tintColor 驱动。App 传的是 `colors.primary + "33"`，所以光标被打成 20% 透明。
改为 cursorColor 优先、selectionColor 兜底。Android 本来就是分开的
（`cursorColor` 染 cursorDrawable、`selectionColor` 设 highlightColor），无需改。

### 3. 样式对齐

- `ArticleRichTextInput`：`htmlStyle` 的 h1~h4 改为 27/22/19/17 + bold、
  blockquote 边框改 `theme.border`，正文基准 15 → 16、lineHeight 23 → 28
  （取自 `picart_next/src/components/article/ql-editor-content.css`）
- `constants/editorTextStyles.ts`：色板换成 web `constants.tsx` 的 71 色
  （`rgb()/rgba()` 原生两端都能解析），字号阶梯换成 12/14/16/18/24/32、基准 16
- 工具栏色板改成一行 8 格的网格（一组色系一行），选完收起面板

注意：RN 文章页 `ArticleHtmlWebView.tsx` 自己那套 CSS 标题是 22/20/18/16、
行高 24，和 web 的 27/22/19/17、28 不一致。本次编辑器按 web 走，**两处仍有差异**，
要对齐得改 WebView 那套。

### patch-package 的坑

`node_modules/react-native-enriched-html/android/build` 是 Gradle 产物，
路径超 260 字符会让 `npx patch-package` 直接崩（`Filename too long`）。
生成补丁前必须把它移出包目录（`mv` 到工程下的临时目录），生成完再移回。
当前补丁：29 文件 / 7 个新增 / 1794 行，`git apply --reverse --check` 通过
（反向校验通过即说明补丁与 node_modules 现状一致）。

## 续：图片回填格式 / 不铺满宽度 / 图片圆角

### 1. `images` 已经是对象数组

后端 `article.images` 从 `string[]` 变成了 `ImageData[]`
（`{ url, width, height, size, auditStatus, original, thumbnails }`），
`app/publish/index.tsx` 的回填还按 `typeof url === "string"` 过滤，导致编辑时
一张图都回填不出来。改成 `(string | ImageData)[]` 双兼容：

- 字符串老数据：只用 `uri`
- 对象：`uri + width + height` 一起带过去，进编辑器不用再量尺寸

`uri` 统一过 `normalizeImageUrl`（自家域名 http→https、根相对路径补 origin）。
提交时 `/^https?:\/\//` 命中就直接沿用，不重复上传。

两条边界（用户明确要求，别搞混）：

- **`images` 数组只属于图片类型（图集）**。文章 / 视频类型不走它，正文图全在
  `content` 的 HTML 里；所以回填时先判 `nextType === "image"`，否则文章类型的
  图会被数组和正文各填一遍。
- **图片只用 `url`，不用 `original`**。`original` 是归档原图（相对路径、
  体积大、不在展示链路上），`lib/image.ts` 的 `getImageUrl` 里它只是 `url`
  缺失时的兜底，回填不碰它。

### 2. 编辑时图片不铺满宽度

图片铺满整行后该行没有可点的空白，光标进不去，那一行就改不了。
`lib/editorHtml.ts` 加了 `ARTICLE_IMAGE_EDGE_GAP = 32`，
`getEditorContentWidth(windowWidth)` = 窗口宽 − `ARTICLE_EDITOR_SIDE_PADDING`(32，
即 `app/publish/index.tsx` 的 `PAGE_PADDING * 2`)。两条路径都减掉 gap：

- 回填：`prepareArticleHtml` 的 `availableWidth`（最终宽 ≤ 窗口 − 64）
- 插图：`ArticleRichTextToolbar.handlePickImage` 的 `maxWidth`

尺寸单位约定：HTML 的 `width/height` 按 **dp**（≈ web 的 CSS px）传，
原生侧再 × density（Android `EnrichedImageSpan.getDrawable`、
`prepareDrawableForImage` 的 `setTargetSize`），所以小图不会被放大错位。

### 3. 图片圆角（12，对齐 web `.ql-image` 的 `border-radius: 12px`）

- **iOS**：图片不是 `NSTextAttachment` 画出来的，而是
  `AttachmentLayoutUtils.mm` 里给每个附件挂的独立 `UIImageView` overlay。
  圆角必须在那一层设（`layer.cornerRadius` + `layer.masksToBounds`），
  在 attachment 上设没用。
- **Android**：`EnrichedImageSpan.draw()` 只把 drawable 画进 bounds，
  bounds 是矩形，没有形状概念。改成 `canvas.save()` → `translate` →
  `saveLayer(bounds)` → `clipPath(圆角矩形)` → 画 → `restoreToCount(layer)`
  → `restore()`。`saveLayer` 是给边缘留抗锯齿，只 `clipPath` 会出锯齿。
  圆角 Path 按 (width,height) 缓存，尺寸不变就不重建。
  `EnrichedInputImageSpan` / `EnrichedTextImageSpan` 都继承这个基类，改一处两端生效。

### 4. 图片居中

web 端图片是块级 + `.ql-image-wrapper { justify-self: center }`；
原生图片是**行内附件**（`ImageSpan` / `NSTextAttachment`），自身没有对齐能力，
对齐只能落在**段落**上（两端都从 `<p style="text-align:...">` 解析：
iOS `HtmlParser.mm:checkForAlignments`，Android `CSS_ALIGNMENT_PATTERN`）。

- **回填 / 重进编辑器**：`prepareArticleHtml` 末尾统一跑 `centerImageParagraphs()`，
  给「段落里只有图、没有正文」的 `<p>` 补 `text-align:center`；
  段里有正文就不动（否则正文一起居中），已有显式 `text-align` 也不覆盖（保留用户手选）。
- **工具栏插图**：`setImage` 没有块级概念，图只会落在当前段里。
  插完 `await editor.getHTML()` 用 `isImageAloneInParagraph(html, url)` 判断这一段
  是不是只有这张图，是才 `setTextAlignment("center")`。拿不到最新 HTML 时按
  「只有图」处理（`getHTML` 的 `requestHTML` 命令与 `setImage` 同队列，顺序可靠）。
- **提交回 web**：`toArticleHtml` 的正则从 `<p>` 放宽到 `<p\b[^>]*>`，
  这样带 `style` 的图片段也能被识别并包回 `div.ql-image-wrapper`，`text-align` 一并丢掉
  （web 用 `.ql-image-wrapper` 自己居中）。

顺手修掉一个幂等 bug：`ql-align-*` → `style="text-align:..."` 的转换原本会叠加，
第二次跑就变成 `text-align:center;text-align:center`；现在 style 里已有对齐就直接跳过。

**遗留**：文字段的对齐提交回 web 只留 `style="text-align:..."`，而 Quill 认的是
`ql-align-center` 类，网页端再编辑时文字对齐会丢（图片不受影响，走 wrapper）。

### 5. 行高改成移动端比例（不吃 web 的 1.78）

web 是 `font-size: 16px; line-height: 1.78`（16/28）。移动端不用这套：

- **编辑器** `ArticleRichTextInput`：`lineHeight: 28` → **26**（16 × 1.6）。
  `lineHeight` 在原库里是**全局**属性（Android `EnrichedLineHeightSpan` 覆盖整段文本、
  iOS `minimumLineHeight`），`HeadingStyle` 没有 per-level 行高；
  好在两端都**只撑大不压小**（Android 的 `chooseHeight` 还显式跳过
  `EnrichedHeadingSpan`），所以 27px 的 h1 不会被 26 压扁。
- **阅读页** `ArticleHtmlWebView`：行高从写死的 px 改成**无单位倍数**——
  `body { line-height: 1.6 }`，标题 `1.35`，`p` / `.ql-size-*` / `.ql-code-block`
  全部删掉 px 行高。无单位倍数是「按元素自己的字号算」，所以
  `ql-size-24px` 这种行内大字号也能自己撑开；写死 px 则会被大字号撑破
  （原来 h5 15/16、h6 14/15 这类 1.07 倍的比例，中文上下会粘）。

**遗留**：`ArticleHtmlWebView.tsx` 有个**既有** eslint 报错
（`react-hooks/refs`：`return renderBody()` 里读了 ref），HEAD 版本同样报，
不是本次引入的；`npm run lint` 会红。

### 6. 编辑器标题字号降到移动端档位

`ArticleRichTextInput` 的 `htmlStyle` 标题原本照抄 web 的 27/22/19/17，
手机屏窄，h1 一行放不下几个字，且和阅读页（`ArticleHtmlWebView` 的
22/20/18/16/15/14）对不上。统一改成 **22/20/18/16/15/14**，
并把 h5 / h6 补上（web 端有 h5/h6 的内容进原生编辑器才有正确字号）。

### 7. 行高「全加在上面」→ 上下均分（half-leading）

原生 `lineHeight` 只会往**一侧**加余量，文字因此贴着行框底部，看起来像行距全堆在字上方；
web 的 CSS 行高是 half-leading（上下各一半）。修法：

- **Android** `EnrichedLineHeightSpan.chooseHeight`：原来只 `fm.ascent -= extra`，
  改成 `extra/2` 同时加给 ascent 与 descent（`fm.top`/`fm.bottom` 跟着扩），
  总行高不变、文字垂直居中。`MeasurementStore` 用的同一个 span，测量高度也跟着一致。
- **iOS** `EnrichedTextInputView.mm`：`pStyle.minimumLineHeight` 是把余量加在文字上方
  （库里 `getTextAlignedUsedRect` 那个补偿就是为此），没法只靠段落样式居中。
  改为额外加 `NSBaselineOffsetAttributeName = (lineHeight - primaryFont.lineHeight)/2`
  （正数=抬高），在 `refreshLineHeight` 里覆盖整段 + 在 `defaultTypingAttributes`
  里也加一份，接着打字不会跳。**这项只在本机验证不了，需要真机看**；
  若发现方向反了，把这个偏移取负即可。
