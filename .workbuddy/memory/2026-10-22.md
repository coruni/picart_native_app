- `app/chat/[id].tsx` keyExtractor 的 `Math.random()` 兜底改为 `local-${index}`。

**额外发现（本轮最大收益）：TabView 默认 lazy=false**
`react-native-tab-view` 不传 `lazy` 会**同时挂载所有 scene**：
- `app/(tabs)/index.tsx`：关注/首页/活动三个列表一起挂载 → 首屏并发三份请求。
- `app/(tabs)/circle/index.tsx`：routes 是**所有子分类**，等于进圈子页就并发十几个 `ArticleList`。
- `app/search/index.tsx`、`app/topic/[id].tsx` 同理。
四处均加 `lazy`。topic 的容器高度来自 `scrollViewportHeight - TAB_HEIGHT`，不依赖 scene 内容，加 lazy 不会引起布局跳动。

**P1-3 结论反转（已回写方案文档）**：`npm ls` 显示 `expo-router` 依赖 `@expo/ui` 与 `expo-symbols`（deduped），二者不是可移除的零引用包，原方案该条作废。

### 后续：列表到底后还能上滑、底部空一条（已定位，两次尝试）

**第一次错误尝试（已回退）**：怀疑 `tabViewMinHeight = scrollViewportHeight - TAB_BAR_HEIGHT` 重复扣了 tab bar，改成 `scrollViewportHeight`。用户验证后确认不是这个问题，`git diff` 已恢复为空。

**用户设备是 Android**（截图：双卡/5G 状态栏、底部导航无 iOS 安全区垫）。iOS 那份
`RNNestedScrollViewHeader.mm` 的分析不适用，改读 Android：

- `NestedScrollViewHeader.getStickyHeight()` = 「折叠后 header 要留在顶部的高度」
  - 传 `stickyHeaderHeight` → 直接用（`PixelUtil.toPixelFromDIP`，JS 侧传 dp 即可）
  - 传 `stickyHeaderBeginIndex=N` → `i >= N` 的 child 高度之和
- `NestedScrollView.fitStickyHeightIfNeeded()`：`maxScrollRange = headerHeight - stickyHeight`

原代码用 `stickyHeaderBeginIndex={2}` → stickyHeight 只有 tab bar 那 40px
→ header 一路滚到只剩 40，tab bar 停在 y=0 钻进状态栏（被顶部头像浮层盖住，截图里 tab 就这么没了）。

**底部空白是两笔账叠加（88 = 48 + 40）**：
1. sticky 过头 48：折叠后只留 40，而 `scrollShell.top = heroMinHeight`(88)
2. `tabViewMinHeight = scrollViewportHeight - TAB_BAR_HEIGHT` 重复扣了 40

只改一处时空白从 88 变 48 或 40，看起来像没修好——上次被否掉就是这个原因。

**但两处一起改后用户要求全部回退（2026-10-22 15:27）**，`app/(tabs)/profile.tsx` 已 `git checkout` 回到 HEAD。说明方向不对：
不是 sticky 高度/内容高度算错，而是「列表到底后父容器继续滚」这件事本身。
后续要动的话，别再碰 `tabViewMinHeight` 和 `stickyHeader*` 这两个参数。

已确认的源码事实（下次可直接用）：
- Android `getStickyHeight()`：`stickyHeaderHeight` 直接生效（会 toPixelFromDIP）；`stickyHeaderBeginIndex=N` 取 `i>=N` 的 child 高度和。
- Android `maxScrollRange = headerHeight - stickyHeight`，`contentHeight = 视口 - stickyHeight`（后者通过 state 传给 JS，但库的 JS 侧根本没用这个值）。
- iOS `maxScrollRange` 用 `headerHeight - stickyHeaderHeight`，beginIndex 分支取 `i<N` 的和（等价语义）。
